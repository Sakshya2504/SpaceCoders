# Testing & Verification Guide

This document provides a practical verification plan for the PatientTriage.ai prototype. It focuses on the behaviors a developer or demo presenter should verify locally.

## 1. Install and start

Verify the JavaScript application starts without import or syntax errors:

```powershell
npm install
npm run install:all
npm run dev
```

Verify:

```text
Frontend: http://localhost:5173
Backend:  http://localhost:3000
```

If the ML service is being tested, start it separately and verify:

```text
http://127.0.0.1:8000/health
```

## 2. Health verification

Open:

```text
http://localhost:3000/api/health
```

Check that:

- the API responds;
- MongoDB reports `ONLINE`;
- the configured AI mode is visible;
- realtime status is present.

## 3. Authentication tests

### Login success

Use:

```text
charge@patienttriage.demo
 demo123
```

Confirm that the browser reaches the Command Centre and stores the authenticated session.

### Login failure

Enter an incorrect password and verify that a useful error is displayed without exposing server internals.

### Signup

Open `/signup` and create a new account.

Verify that:

- name is required;
- email validation works;
- password confirmation is enforced;
- successful signup creates an authenticated session;
- the default role is `triage_nurse`.

## 4. Patient creation test

Open **Patient Intake**.

Enter a normal synthetic patient.

Verify:

- patient ID is generated by the application;
- derived features update correctly;
- the patient is created successfully;
- a triage result is returned;
- the browser navigates to Patient Review.

## 5. Dataset-aligned feature test

Check that the intake payload contains the expected model feature names.

Important derived values to verify manually for a sample case:

```text
BMI
Mean arterial pressure
Pulse pressure
Shock index
Age group
Arrival hour/day/month
Arrival season
Shift
```

Do not enter `patient_id`, `disposition`, `ed_los_hours` or `triage_acuity` as operator inputs to the inference contract.

## 6. Red-flag tests

### Respiratory case

Use a synthetic case such as:

```text
SpO2: 82
Respiratory rate: 34
Complaint: severe shortness of breath and blue lips
```

Verify:

- respiratory detector becomes positive;
- recommendation enters immediate escalation;
- the patient is visible in the alert center;
- the audit trail contains escalation activity.

### MI-like case

Use:

```text
Chest pressure
Radiation to left arm
Diaphoresis
Nausea
```

Verify that the independent MI-like detector records the expected signals.

### Stroke-like case

Use:

```text
Sudden facial droop
Speech difficulty
Weakness
```

Verify that the stroke-like detector recognizes the complaint signals and can drive higher urgency.

### Sepsis-like case

Use a synthetic combination of fever, tachycardia, high respiratory rate, low systolic BP and altered mental status with infection context.

Verify that the independent detector contributes to escalation.

## 7. Confidence and uncertainty tests

Create a patient with complete information and history.

Then create a patient with:

```text
hasHistory = false
```

Verify that:

- history is displayed as unavailable/zero-history;
- confidence decreases;
- the explanation identifies reduced history confidence.

For a sparse case, verify the explicit `ABSTAIN_AND_ESCALATE` path where the completeness/confidence threshold is met.

## 8. XGBoost inference test

Train the local model:

```powershell
python ml/train_xgboost.py --data train.csv
```

Start the inference service:

```powershell
uvicorn ml.inference_service:app --host 127.0.0.1 --port 8000
```

Check:

```text
GET http://127.0.0.1:8000/health
```

Then submit a patient through the Node application and verify that the stored triage result identifies the model source when XGBoost is available.

The exact displayed source/version should match the service response and stored patient metadata.

## 9. Fail-open test

Temporarily stop the Python inference service and trigger a new triage or reassessment.

Verify:

- the browser request completes rather than hanging;
- the Node service falls back to its deterministic scorer;
- the stored result exposes the fallback source;
- the workflow remains available for manual review.

Restart the Python service afterward.

## 10. Patient identifier test

Open a seeded patient using its application identifier:

```text
PT-2026-001
```

Verify that the backend fetches the patient without a MongoDB ObjectId cast error.

The application must also continue to support a valid MongoDB `_id` when such an identifier is used internally.

## 11. Clinician accept/override tests

### Accept

Open Patient Review and click **Accept**.

Verify:

- the request succeeds;
- a clinician-accepted audit event is created;
- the model recommendation remains distinguishable from the final decision.

### Override

Choose **Override**.

Verify that:

- target ESI must be 1–5;
- structured reason is required;
- optional note is stored;
- the final ESI changes to the selected target;
- the audit trail contains the override event.

## 12. Queue tests

Open **Live Queue**.

Verify:

- waiting patients are listed;
- position is displayed;
- ESI and confidence are visible;
- wait time is calculated;
- action tier is displayed;
- red-flag count is visible.

Click **Reassess now** and verify that the request completes and the queue refreshes.

Toggle **Surge mode** and verify that the operating state changes.

## 13. Deterioration test

Use a patient that is already waiting and simulate a worsening clinical state through the reassessment workflow.

Verify:

```text
Previous ESI
      ↓
New ESI
      ↓
Deterioration detected
      ↓
Realtime alert
      ↓
Audit event
```

## 14. Alert tests

Verify that realtime events can populate the alert center.

Test at least:

```text
Triage recommendation
Immediate escalation
Deterioration
Clinician override
Fail-open
Surge completion
```

Verify:

- unread count updates;
- alerts can be marked read;
- alerts can be dismissed;
- critical events produce a visible toast.

## 15. Audit-chain verification

Open **Audit Trail** and click **Verify chain**.

For an intact chain, confirm:

```text
CHAIN VALID
```

and a count of verified events.

The API should identify the first broken event when a chain mismatch is detected.

## 16. Responsive UI test

Test the frontend at approximate widths:

```text
1440 px  Desktop
1200 px  Narrow desktop
900 px   Tablet
640 px   Phone
400 px   Small phone
```

Verify:

- no accidental page-wide horizontal scrolling;
- intake fields collapse cleanly;
- tables remain usable through local horizontal scrolling;
- alert panels fit the viewport;
- buttons remain tappable;
- navigation remains usable.

## 17. Regression checklist

Before a final demo, run:

```text
[ ] Frontend starts
[ ] Backend starts
[ ] MongoDB connects
[ ] Health endpoint works
[ ] Login works
[ ] Signup works
[ ] Seed works
[ ] Patient creation works
[ ] Patient review works
[ ] ESI displayed
[ ] Confidence displayed
[ ] Red flags displayed
[ ] XGBoost service works when enabled
[ ] Fail-open works when ML is unavailable
[ ] Queue loads
[ ] Reassessment works
[ ] Surge mode works
[ ] Accept works
[ ] Override works
[ ] Alerts appear
[ ] Audit chain verifies
[ ] Responsive layouts work
```

## 18. Test-data safety

Run these tests only with synthetic data. Never point `seed` at a production database.

## 19. Limit of testing

Successful software tests demonstrate that the prototype behaves according to its implemented logic. They do not establish clinical validity, safety in real patient populations or regulatory compliance.
